# AI協作紀錄

## 使用工具

- 使用 Codex 作為 AI 程式開發協作者，在既有 BIM Viewer 專案中閱讀程式、提出及實作修改、整理測試結果與文件

## Prompt

- 開發過程中，我主要使用VS Code搭配Chatgpt與Codex協助撰寫程式、修改功能及排查錯誤，我不會一次把所有功能都交給AI開發，而是先確認目前要完成的功能，再逐步實作和測試

Prompt 1：希望先理解再繼續開發

我要一步一步做，不要一次把所有功能都丟給Codex，每完成一個功能，就先實際測試，確認沒問題再繼續做下一個

Prompt 2：限制AI修改的範圍

先不要刪除或覆蓋任何檔案，也不要另外建立一個巢狀專案，直接在我建立的 VS Code專案資料夾裡修改，不要動到跟目前功能無關的地方

Prompt 3：遇到錯誤時先找原因

先檢查目前的程式碼和錯誤原因，再針對問題修改，不要直接重建整個專案，如果是檔案路徑有問題，就先確認檔案實際放在哪裡，不要為了配合測試就直接移動或刪除檔案

Prompt 4：完成後要實際驗證

修改完成後，請實際執行測試、Build、Lint和TypeScript 檢查，並告訴我哪些通過、哪些失敗，如果測試失敗，要說明實際原因，不要直接說全部完成

Prompt 5：保留原本的工作成果

不要執行git reset或git clean，不要刪除我原本的修改和未追蹤檔案，也不要自行commit或push GitHub，修改前先確認目前的Git狀態

## 驗證 AI 生成的程式碼

一開始我會先確認工作目錄、現有架構、Git狀態，避免重建專案或刪除現有的檔案，接著檢查package scripts、IFC Worker、Three.js場景、GLTF資源處理與專案 JSON 驗證程式，對照實際檔案路徑，不只是依賴AI判定

除了讓Codex執行測試，我也會自己操作網頁確認功能是否正常，像是實際匯入 IFC和GLB模型，測試物件選取、高亮、相機控制、移動、旋轉、縮放、刪除，以及專案儲存後重新開啟的結果

如果命令列測試失敗，我會再確認是程式本身有問題，還是測試檔案路徑不正確，不會只因為AI說完成就直接認定功能正常

透過這種方式，我將AI當作協助開發與排查問題的工具，實際功能是否完成，仍然會透過自己的操作和測試結果來確認

## 開發過程中遇到的挑戰與解決方案

1. AI 修改程式時可能影響原本已完成的功能

專案逐漸增加功能後，我發現如果一次要求AI修改太多內容，可能很難確認問題是從哪裡產生，也容易影響原本已經完成的功能。因此，我改成一次處理一個明確的任務，並要求AI在修改前先檢查現有程式碼與Git狀態，避免重建專案或清除原本的修改

每完成一個階段，我都會重新執行測試，並在瀏覽器中實際操作確認，例如，模型匯入後除了檢查程式是否成功執行，也會確認能否選取物件、操作變換工具，以及儲存專案後重新開啟

2. 自動化測試通過不代表所有操作都已經確認

開發初期，我除了使用AI協助撰寫測試，也需要確認測試結果是否真的符合使用需求。例如，測試可以確認 GLB 模型是否成功解析，但不一定能完整確認使用者拖曳模型後，移動、旋轉與縮放的結果是否正確保存

因此，我將驗證分成自動化測試和實際操作兩個部分。前者用來檢查程式執行、模型解析及基本資料處理；後者則由我親自在瀏覽器中操作，確認模型變換、專案儲存、重新開啟及變換狀態還原是否正常

3. IFC模型解析與資源管理

在開發IFC模型匯入功能時，遇到第三方套件API與原先程式碼預期不一致的問題，導致模型解析流程發生錯誤。我透過檢查套件的實際回傳資料，修正不適用的API呼叫，並增加幾何資料驗證，確認模型能正確解析，此外，也將 IFC 解析工作交由Worker處理，並規劃模型清除時的資源釋放機制，以提升程式的穩定性

4. GLTF模型的相依檔案處理

開發GLTF模型匯入功能時，發現部分模型除了主檔案外，還需要額外的幾何資料或貼圖檔案，由於瀏覽器的檔案選取機制無法直接存取任意磁碟路徑，因此設計了多檔案或資料夾匯入方式，並加入相依資源檢查，讓程式能在必要檔案缺漏時提示使用者，降低模型載入失敗的情況

5. 專案儲存與模型還原

在實作專案儲存與重新開啟功能時，發現單純保存模型路徑及變換參數，無法確保重新開啟時使用的模型與原先一致，為此，設計以JSON保存模型識別資訊、檔案大小、SHA-256雜湊值及移動、旋轉、縮放參數的機制。重新開啟專案時，讓使用者重新選取模型並比對檔案內容，確認一致後才還原變換設定，以避免錯誤模型套用舊有參數。
